# CAN1 / CAN4 共享 SPI 与 IMU 实板压力测试

2026-10-06，用户确认CAN1/CAN4短接。CAN4为MCP2518FD，与BMI088、LSM共用SPI4；保持10MHz SPI、P0 CAN1/2/3和IMU/INS、P1 CAN4及正式后台服务。测试工程见 [CAN4SPILoad](../../../Tests/Board/CAN4SPILoad/README.md)，生产驱动、IOC、API和资源配置没有在本次测试中修改。

当前CAN4不能按每路同时3000 RX＋3000 TX帧/s验收。Classic双向各2k时CPU已约91.5%，请求各3k时生产者错过周期，实际只有各1.54k。FD5M、64B双向各3k时出现MCP RX FIFO溢出和实际丢帧。SPI事务本身成功不能代表CAN帧不丢失，也不能把未收到提交背压当成吞吐达标。

默认8M配置未进入负载阶段；表中8M数据只能代表测试专用时序。Classic/FD2M/FD5M/FD8M对齐共44个窗口、379秒，正常模式功能帧228/228、对齐快速probe64/64；另外两次默认8M首帧检查失败，不能用整体执行完成掩盖这些失败。

## 负载与测量口径

各方向是CAN1→4 / CAN4→1；双向各3k在同一物理CAN线上合计6000帧/s，每帧一次发送、一次接收，不重复计算两端计数。负载使用标准ID 0x601/0x604，功能检查同时覆盖标准/扩展ID、Classic全部0–8B长度及FD全部合法DLC、全payload和flags。未测RTR。

每个完整镜像先等待INS VALID，再稳定3秒；不以此宣称温稳或姿态精度通过。一个1ms、优先级24、2048B栈的托管生产者按窗口批量提交，不追赶错过的周期。Classic各3k和FD8M对齐配置各3k窗口持续60秒，其他目标档5–10秒。CPU是整窗Idle runtime差值，含ISR、生产者及所有背景服务；窗口内不暂停调试器、不读CDC、不扫栈。全部结束才扫栈并停在唯一测试断点导出结果。

`received_active`为活动窗口实际收帧，`received`包含停发后500ms排空，软件TTL为100ms。`achieved`同时检查生产周期、实际速率、拒绝、缺序、损坏和接纳后交付；生产者降速不算通过，活动窗边界少数在途帧不直接等于丢帧。SPI四设备快照在活动窗口前后读取：直方图为差值，max_queue/max_transfer是启动以来峰值，不能当成本档独立峰值。IMU observer逐样本记录完成间隔和采集耗时，观测开销也在CPU中。

完整逐档数据见 [负载表](loads.md) 与 [摘要](summary.json)。这是当前批次、ID、短接拓扑的短测，不是四路CAN、UART、外部独立发生器、长期运行或最坏控制延迟证明。

## CAN4 的两个独立问题

**8M默认位时序不兼容。** 原配置首帧CAN1→4、0B、标准ID、BRS即失败；CAN1发生一次Bus-Off，恢复后ECR累计错误32，MCP REC=32且未收到功能帧。带预热的完整镜像和不带预热的快速probe均复现。CAN1仲裁采样点76.25%，MCP为80%；数据段两端均80%。测试专用链接wrap只将CAN1仲裁段TSEG1/TSEG2从60/19改为63/16，仍为1M，保持数据8M与TDC；随后64/64双向格式用例通过，TEC/REC/Bus-Off为0。生产配置仍未修正，不能将对照结果写成默认8M已可用。

这一对照支持先修正跨控制器仲裁采样点一致性。[Microchip参考手册3.4.7节](https://ww1.microchip.com/downloads/en/DeviceDoc/MCP251XXFD-CAN-FD-Controller-Module-Family-Reference-Manual-20005678B.pdf)说明，不同采样点会在BRS/CRC分隔符切速时引入相位误差。这里没有外部示波器波形，因此不宣称已排除线束、终端和收发器的全部高速裕量问题。两种快速probe仅用于功能诊断，不用于IMU/压力验收。

**CAN4收发处理能力不足。** Classic单向3k、8B两个方向均完整交付；双向各2k时CPU91.54%，MCP约18998笔SPI事务/s。请求各3k的60秒中生产者只执行30845/60000周期，实际各1542帧/s，接纳帧虽均交付仍未达到目标。各4k/5k请求的实际速率受批次与周期跳过影响，不能把某一档实际值当作CAN4恒定最大吞吐。

FD5M、64B单向3k两个方向均完整交付。双向各2k的10秒窗最终接纳/交付各19994帧，生产者少执行3个周期，CPU86.65%，属于约2k短测而非严格周期验收。双向各3k的10秒窗，CAN1→4接纳29946、只交付10437，丢失19509；CAN4→1交付29464，提交拒绝482。MCP硬件RX溢出计数增长314；该值是溢出事件次数，不是丢帧数。四组SPI queue_full/queue_expired/errors/timeouts/recoveries均未增长，说明这里丢的是来不及搬出的CAN帧，不是SPI传输报错。

FD8M仲裁采样点对齐后的64B、各3k、60秒窗口：实际1204.27 / 2835.49帧/s，CPU89.01%，生产周期59517/60000；CAN1→4接纳178551、交付72272、丢失106279，CAN4→1交付170151、提交拒绝8400，MCP硬件RX溢出1887次。TEC/REC和SPI错误/超时为0。与5M一致，提高线速没有消除CAN4处理瓶颈；不能把原生CAN1/3已经通过的8M吞吐外推给外置CAN4。

FD2M格式检查64/64通过，64B单向3k均完整交付；双向各3k时实际2939.84 / 229.61帧/s、CPU91.96%，CAN4发送拒绝22978次并过期4051帧。此时无MCP硬件RX溢出，接纳后差额全部由TTL解释，与2M带宽及低ID优先仲裁的限制一致。四个完整镜像的末档8B各1k都恢复交付，不能由此推导更高档长期可持续。

源码中的每帧多次同步SPI事务、DMA完成唤醒和CAN4 RX/TX共享锁，是后续优先剖析对象；本次没有逐函数CPU或锁持有时间采样，不能将CPU百分比全部归给SPI ISR，也不能从事务次数直接推导SCK线占用率。Classic `rx_overflow`仅指可覆盖调试日志环，实际接收丢失须看应用序号、`rx_hw_overflow`等。

## IMU 与余量

统计范围、各模式峰值与资源水位见 [观测汇总](observations.json)。样本完成间隔包含调度抖动，不等于IMU内部采样时钟；采集耗时也不等于纯SPI排队时间。CPU高占用或CAN4过载时IMU仍能被优先服务，只证明本次P0保护有效，不意味着CAN4已达标。

44个窗口中双IMU各379000个样本，INS同为379000次发布，missing/missed均零；各传感器errors/overruns均无增长。BMI/LSM最大样本完成间隔分别1127/1138µs，无超过1500µs间隔；最大采集耗时190/175µs。四组SPI排队满、排队过期、传输错误、超时和恢复计数增量均0。

SPI启动以来排队峰值（BMI加速度/陀螺、LSM、MCP）为121/41/111/237µs。Classic双向各2k的每秒事务为2000/1000/2000/18998.1，合计约24000笔；这包括大量短寄存器访问及DMA/任务往返，不能按64B或8B数据字段估计全部开销。各镜像全负载后最小剩余栈：CAN4 RX3172B、TX3068B、SPI2480B、BMI1388B、LSM1444B、INS1996B、生产者1468B。运行期内核heap最低空闲62080B，测试任务对象峰值2304B、删除后0B；只是本应用水位，不授权缩减生产资源。

身份记录仍有启动读取状态6（CORRUPT），参数加载成功；本次不写EEPROM，也不依据身份记录状态推断全部校准损坏。LIS环境磁力计的低于100Hz窗口与既有记录一致，不能将双IMU/INS连续性扩展为所有传感器均严格按目标频率运行。温稳/校准精度、外部UART混合负载以及四路同步压力仍需独立验证。

## 证据与复现

固定结果结构26816B，短枚举ABI由GDB布局与Python decoder校核。七个测试目标构建、ELF内存/强通知符号检查以及七条应用公共include隔离检查通过；详见 [结构检查](structure-final.log)、[ELF检查](elf-check-final.log)、[公共头隔离](include-check-final.log)。额外观测缓冲仅在测试镜像中，不是生产Minimal内存消耗。

Classic、FD5M和最初FD8M用初版镜像；其余镜像增加功能提前失败的端点快照，Aligned另有测试专用采样点wrap。两版ELF和源码哈希、结果映射见 [manifest](manifest.json)；不能用后编译ELF冒充前三个窗口的原镜像。完整ELF、原始Flash、构建/J-Link日志保存在本机 `build/can4-spi-board-20261006/`；原始结果bin及 [GDB记录](gdb.log)随此报告归档。
