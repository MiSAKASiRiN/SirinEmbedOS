# CAN4 单服务与 SPI 序列优化验证（2026-10-06）

本记录对应 CAN1↔CAN4 实际短接、SPI4 10MHz、双 IMU/INS 与温控开启。最终Classic硬验收通过，原1MiB Flash已恢复并读回一致，探针释放。

## 实现与资源边界

CAN4 RX/TX 合并为 P1/47 的一个 4KiB 服务线程，独占硬件、诊断和错误恢复；CAN1/2/3 与 BMI/LSM/INS 仍 P0/48，SPI4 分发者49。正常4RX/4TX、首次状态发现半满立即8RX/1TX，每帧收集事件，单轮32帧或1ms后Yield，待办保留；空闲最多5ms兜底。持续过载的Yield不保证低优先级应用获得CPU。

MCP 初始化沿用供应商，运行期冻结 FIFO 配置、合读状态/UA、按长度读写。Classic每帧3笔SPI，长FD RX4笔；最多4步×74B的私有序列仅一次调用者唤醒，各步CS释放后重新仲裁。IMU可在每步边界插入，原4＋4槽位、两级4:1公平性和5ms总期限保留。只有完整RAM成功才提交UINC；TX同写UINC/TXREQ，不确定时保留在途并读UA确认，异常UA隔离方向，不清FIFO或盲目重放。

Classic core 增加单帧TX步进，保留adapter周期、group、urgent批次和one-shot TTL；连续one-shot每16帧让adapter获得一次周期机会，剩余one-shot立即续跑。公共函数签名和帧结构不变，CAN4回调上下文变为唯一P1服务，回调必须有界、非阻塞且锁外执行。

原生FD仲裁采样点80%；数据≤4M为80%、5M为75%、8M为80%，TDC同步匹配，Classic原时序保持。未修改IOC/生成代码、HAL、供应商、IMU/INS/温控、DMA/MPU/链接布局及SPI4 10MHz设置。

第一版序列优化仍受高频时间换算及任务通知开销影响。因此增加整数MHz微秒商/余数缓存，减少逐次64位除法；长间隔或频率变化仍做精确绝对换算，时间来源不变。SPI使用直接任务通知并复用每轮时钟快照。此组改动与热路径O2共同降低CPU，未做单因素因果归因。新增状态均静态D1，无运行期分配或ITCM增加；CAN线程8→7，栈8→4KiB，保守启动基础heap预算64→60KiB。

## 验证方法

生产者优先级24、真实1ms周期，单周期按目标提交，不补发追赶或主动降速。每帧携带方向、阶段和连续序号，校验完整payload；提交拒绝和TTL单列，接纳帧全部排空后核对接收，不能用降速后的零丢失冒充达标。CAN方向数组为CAN1→CAN4、CAN4→CAN1。

正式镜像关闭详细逐帧计时，保留既有后台服务及轻量观测。每10s按Idle增量计算整板CPU；任务CPU来自Monitor异步采样平均，分项不能要求与整窗精确相加。SPI公开统计按物理事务，包含空状态查询；DMA launch attempts为调用启动路径的次数，错误时不等价于硬件真正启动。活动窗口不暂停、不扫栈、不读CDC；阶段间排空500ms并经唯一CAN4线程读取寄存器，全部窗口后才扫栈。

IMU完成间隔及采集耗时由每个真实样本采集时间记录；SPI排队峰值为自启动以来保守峰值，直方图才是阶段增量。CAN4 `rx_overflow` 是可覆盖调试环，不代表硬件丢帧；硬件看 `rx_hw_overflow`，端到端看序号和接纳/接收数。CPU≤60%只作为Classic目标档硬条件，FD与过载档如实报告。

## 短期定位与中间版本

优化前基线见 [旧报告](../CAN4-SPI-20261006/README.md)：Classic各2k整板CPU91.54%，请求各3k生产周期不足；FD64B各3k发生MCP硬件溢出。第一版合并/序列实现仍未达标：Classic请求各3k实际约2.75～2.78k、CPU76.1～76.2%；各4k档最大IMU采集213µs触发保护线。保留 `classic-quick` 失败数据，不能与最终结果混用。

随后时间换算、直接通知与热路径优化后的 `classic-v2` 短测各3k约53.45%，各4k约65.17%，全部IMU保护线通过。`classic-long-a` 中间镜像已完成3×60s＋600s、最高十秒CPU53.50%，但最终又修正了首次半满预算即时切换和adapter周期结束后立即续发one-shot，因此最终判定仍重跑完整验收。

详细计时镜像 `classic-profile` 各档1s，仅用于定位，不做验收。各3k档MCP19990～19996次物理事务/s，约3.335～3.336次/已处理帧（含空查询）；SPI总DMA启动尝试约24990～24996/s，其余约5000/s来自IMU。CAN4每秒约999次主动休眠后唤醒，每帧序列仍只有一次调用者最终完成通知；两者不是同一计数。

详细计时的单次RX/TX处理峰值分别76/81µs（该时刻启动以来），包括等待SPI和被抢占的墙钟时间，不是纯CPU。若把所有RX调用耗时除以有效RX帧数约85µs/帧，因为分子包含空状态检查，不能将这个摊销值与单次峰值直接比较。正式CPU和任务分项采用关闭详细计时的最终镜像。

## 原固件恢复与证据

独占J-Link 10114514，连接前检查没有其他会话；开始前完整备份0x08000000～0x08100000，每个测试镜像下载后比对向量/text/rodata。所有观测窗只在结束断点取证。结束恢复原1MiB，GDB整段比较与独立读回逐字节均一致，SHA256：

`b5731bd2d67c16d0b1ef66a50cf234b712d1b512d07b6f115209b6d350d08b2a`

复位后两次检查HAL/RTOS tick递增、CFSR/HFSR为0；释放GDB/J-Link，再用CDC1只读HostLink监测验证原固件运行。完整证明见 `restore-check.json`、`gdb.log` 和 `restored-hostlink/`。板上留的是测试前原固件；优化代码及测试保持未提交，未写EEPROM。

所有原始主结果bin为26816B，额外perf为version1/8388B或version2/8564B；可用Tests/Board/CAN4SPILoad两个decode脚本重建JSON。`manifest.json`记录镜像/结果/源码输入哈希，完整Flash与ELF留在本机 `build/can4-opt-20261006/`，未纳入源码。离线检查日志、失败中间版与最终版分别命名。

本轮不覆盖CAN2/3与UART同时满载、真实电机/VT03业务协议、长线/多节点电气极限、主动断线/Bus-Off或真实SPI故障注入；故障序列的确定性由主机模型覆盖。FD过载仍接近IMU保护线（采集194µs、排队144µs），保留余量限制。CAN4为减少SPI取消了逐唤醒CiINT读取，旧CiINT派生调试字段及tx_complete_events保留ABI但不累计；TX提交计数不能替代端到端交付确认。
